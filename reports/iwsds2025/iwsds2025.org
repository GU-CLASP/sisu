#+begin_abstract
The rise of LLM-based approaches to dialogue systems has created an increased need for controllable dialogue. This paper addresses this need by presenting an implementation of a dialogue system based on information state update approach according to [cite/t:@larsson_issue-based_2002]. This enables the integration of rule-based handling of dialogue, expressed by Harel's statecharts, and Larsson's theoretical account grounded in theories of dialogue, expressed by information state update rules. We demonstrate how our approach applies to dialogue domains involving form-filling. We also propose how LLMs can be employed to inject domain knowledge and be used in various components of a hybrid dialogue system, while maintaining control over the overall dialogue logic.
#+end_abstract
* Introduction
\Glspl{llm} remain undeniably uncontrolled, but their capabilities
have raised the bar for conversational AI. This makes a compelling
argument for using rule-based approaches to mitigate the risks associated
with using \glspl{llm}.

In this work we are using an influential framework called
\gls{isu} [cite:@larsson_issue-based_2002]. The basis of this framework is a representation of the
dialogue context as data structure which includes the information
available to each participant of the dialogue (either a human or an
artificial agent). Being rich entails that the information state
contains a hierarchy of facts, including the ones that are thought to
be shared and the ones that have not been yet publicised.

In controlled \gls{isu}-based systems, \glspl{llm} offer benefits such
as pre-generating dialogue domains [cite:@larsson_pre-generative_2024]
and generating natural language responses.

There is a body of theoretical work on human-human dialogue [cite:e.g., @cann_dynamics_2005;@ginzburg_interactive_2012;@cooper_perception_2022], which can be helpful for designing dialogue systems producing acceptable and natural behaviours. As a first, proof-of-concept step, \gls{sisu} implements a version of IBiS1 [cite:@larsson_issue-based_2002]. 

In our proposed framework, \gls{sisu}, we combine the statecharts formalism
[cite:@harel_statecharts_1987] with modern features of the TypeScript programming
language. This allows us to run dialogue applications in both frontend
(in-browser voice-enabled dialogue) and backend (controlling social
robots, running automated tests) environments.

\Gls{sisu} improves upon [cite/t:@larsson_issue-based_2002] work by
providing the capacity to code parts of a dialogue domain using
statecharts. This is particularly useful for domains and aspects of
dialogue that have only a procedural description.

** Statecharts
Statecharts were originally developed by
[cite/t:@harel_statecharts_1987] for complex systems (real-time,
multi-computer and concurrent). In its basis it is just a
deterministic \gls{fsm}. [cite/author:@harel_statecharts_1987] introduces
conventional notation over \glspl{fsm}, incorporating depth,
orthogonality and broadcast communication.  Statecharts can be
represented graphically, as diagrams with a variable level of
detail.

Figure [[fig:sc]] shows an example of a statechart which
represents a sequence of speaking and listening. In this case,
speaking involves two orthogonal processes denoted by a dashed line, one represents a call to a \gls{llm} and another -- a request to a \gls{tts} module to speak from the stream generated by the \gls{llm}. When the \gls{llm} is done streaming (\texttt{DONE} event) and the \gls{tts} module is done speaking (\texttt{SPEAK\_COMPLETE} event), both orthogonal process reach their final states, and the machine can transition to \texttt{Ask} state using the transition defined for the \texttt{Respond} parent state  which encloses two orthogonal states. Actions performed by the systems are denoted by a "/" symbol.

** Update rules

Update rules consist of preconditions and effects. For instance,
rule \eqref{eq:isa} written in Prolog-based IBiS1
[cite:@larsson_issue-based_2002 rule 2.2], checks whether the latest
utterance is produced by the system and that the move type is
\texttt{ask} and it contains a question $Q$. In effect, the question
$Q$ (in IBiS1, it is a bound Prolog variable) becomes a \gls{qud} gets pushed onto the
stack of \glspl{qud}.
#+begin_export latex
\begin{equation}\label{eq:isa}
\begin{array}{rl}
\text{\textsc{pre:}} 
  &\left \{ \begin{array}{l}
  \text{\$\textsc{/shared/lu/speaker}} == \text{\texttt{sys}} \\
  \text{in}(\$\textsc{/shared/lu/moves}, \text{\texttt{ask}}(Q))
  \end{array} \right. \\
\text{\textsc{eff:}}
   &\left \{ \begin{array}{l}
   \text{push}(\textsc{/shared/qud}, Q)
   \end{array} \right. \\
\end{array}
\end{equation}
#+end_export


In SISU, update rules have the following type
#+ATTR_LATEX: :options fontsize=\small
#+begin_src typescript
type Rule = (
  context: TotalInformationState,
) => ((x: void) => InformationState) | undefined;
#+end_src
which takes an information state as input and, depending on the truth value of the precondition, either, if the precondition is not met, returns ~undefined~, or else a function that returns the updated state.[fn::XState’s ~assign()~ method is used when the rule is instantiated. ]

Below we show how \eqref{eq:isa} is transformed:
#+ATTR_LATEX: :options fontsize=\small
#+BEGIN_SRC typescript
integrate_sys_ask: ({ is }) => {
  if (is.shared.lu!.speaker === "sys") {
    for (const move of is.shared.lu!.moves) {
      if (move.type === "ask") {
        const q = move.content;
        return () => ({
          ...is,
          shared: {
            ...is.shared,
            qud: [q, ...is.shared.qud],
          },
        });
      }
    }
  }
};
#+END_SRC
Note that we make use of spread (~...~) syntax, which effectively allows overriding parts of information state as well as operating stacks (i.e. pushing a question $Q$ into the stack of \glspl{qud}). [fn::[cite/t:@ginzburg_interactive_2012;@cooper_perception_2022] use asymmetric merge operation for expressing updates of an information state. For JavaScript object literals, when one object is spread into another, the property can be overridden by the last assigned value. ]

* Example application
To illustrate how \gls{sisu} can be used to create concrete implementations, we demonstrate an example application involving slot-filling. Specifically, the application enables users to get information about where a lecture takes place, as illustrated by the following example of a supported dialogue (S=system, U=user):

#+begin_export latex
\begin{dialogue}
  \speak{S} Hello! How can I help you?
  \speak{U} Where is the lecture?
  \speak{S} Which course?
  \speak{U} Dialogue Systems 2
  \speak{S} Which day?
  \speak{U} Thursday
  \speak{S} The lecture takes place in G212.
\end{dialogue}

* Integrating \gls{sisu} with \glspl{llm}
Linguistic and non-linguistic capalities of \glspl{llm} can potentially be used together
with \gls{sisu} in various ways. One of most evident applications of \glspl{llm} in
the context of controlled dialogue systems is to use them for \gls{nlu} and/or \gls{nlg}. For example, an
\gls{llm} can be prompted to parse a user utterance into a formal expression
representing one or more dialog moves.

Another possibility is to use \glspl{llm} for pre-generating domain
knowledge, with the dialog developer in the loop
[cite:@larsson_pre-generative_2024]. In the context of \gls{sisu}, an
\gls{llm} can potentially generate dialog plans and database integrations,
e.g., by providing the \gls{llm} with the type definition for a domain, and
example dialogs between system and user.

In contrast to dialog systems that use \glspl{llm} in an end-to-end manner,
leaving the floor open for hallucinations and other potential risk
associated with uncontrollability, the kinds of integrations discussed
above reap the benefits of \glspl{llm} while allowing the dialog developer to
maintain full control over the dialog management logic. In future work, it would be
interesting to explore these possibilities further.
